# Linux/TLS soak and Redis outage, 2026-11-26

Reproduce with `python examples/websocket/soak/run.py all` (Docker only).

**Topology:** 2 gateways + worker + router + Redis 7.4 (AOF everysec), nginx TLS proxy (`proxy_read_timeout 120s`), `cluster` example binaries built for Linux/amd64. Everything ran in Docker Desktop on one Windows host (16 CPU, ~6 GB for the VM), so the load generator, proxy and nodes compete for the same CPUs. Plain delivery over Redis, signed broker messages (`AuthRequired`).

These are single-machine measurements. They do not show capacity on dedicated hardware, and a shared host probably inflates latency.

## Results

| Test | Result |
|---|---|
| Capacity, 10,000 idle connections via TLS (5,004 + 4,996) | 0 connect errors, 0 readiness flaps. Heap about 17.5 KB and 4.4 goroutines per connection. Gateway RSS about 270 MB each; nginx 1.1 GB. |
| Soak 30 min, 1,000 connections, rooms of 5, 1 msg/s each, 5% slow readers | 9,000,000 / 9,000,000 deliveries, 0 missing, 0 duplicate, 0 errors, 0 readiness flaps, 0 lease failures. Goroutines flat (2815 → 2815). |
| Soak 15 min repeat, heap measured after forced GC | Heap -2.2% / -1.9%, goroutines -1.4% (no growth). The first run's +9.7% / +31% was unforced `HeapAlloc` sampling noise. |
| Slow-consumer disconnects (15 min repeat) | 0 at 5% readers delayed 100 ms each read. |
| Redis stopped 30 s | Connections stayed 1000 → 1000 → 1000, 0 client errors. Both gateways went not-ready during the outage (8 s sampled not-ready), ready again 1.6 s after Redis returned. A fanout after recovery delivered 2500/2500. No gateway restart. |
| Redis stopped 5 min | Connections stayed 1000, 0 client errors. Not-ready for 275 s, ready 10.8 s after Redis returned, post-recovery fanout 2500/2500, no restart. 29 lease failures counted. |

## Not met or not measured

- **Latency SLO not met.** Fan-out p50/p95/p99 was 121 / 237 / 587 ms with 5% slow readers, and 131 / 244 / 277 ms with none (3 min). The target is p99 < 150 ms. A 200-connection smoke run was p50 29 ms, p99 51 ms, so latency grows with load on this host. The cause is not isolated (shared CPUs, the sender-to-room Redis path, or the code).
- **Message loss during the outage was not measured.** Only post-recovery delivery was verified. No traffic was sent during the outage, so the loss window is unknown.
- **kill -9 of a node and the 100% reconnect storm were not run**, nor NATS outage, nor 24 h soak, nor 5,000 connections *with* traffic (capacity run was idle).
- The load generator reports one delivery per room recipient; the Redis outage runs used idle connections, not active chat.
- The 10,000-connection run was idle; memory per connection under traffic is higher (soak: about 38 MB heap for 500 connections per gateway including queues).
