# WebSocket client protocol: errors, close codes and reconnect

This describes what a client sees when the server refuses, warns or ends a
session, and what the client should do. It covers the server in `websocket/core`
and the four adapters (net/http, Gin, Echo, Fiber). Application event types and
payloads are defined by your own handlers and are out of scope.

Everything below is a **best-effort signal**. A close frame and an `error`
envelope are written with a short deadline (`WriteWait`, default 10 s). A dead
network, a proxy that swallows frames or a client that stops reading ends in
close code **1006** (abnormal closure, generated by the client library, never
sent by the server). Treat 1006 as "unknown, reconnect with backoff".

## 1. Before the upgrade: HTTP status

The server decides these before it completes the WebSocket handshake, so the
client gets an HTTP response, not a socket that opens and closes. Browsers hide
the status and body of a failed handshake; native clients can read them.

| Status | Body `error` | Meaning | Client action |
|---|---|---|---|
| 426 | `upgrade required` | Request is not a WebSocket upgrade | Fix the client; do not retry |
| 401 | `unauthorized` | Authentication failed or no identity | Refresh credentials, then retry once; do not loop |
| 403 | plain text, not JSON | Origin rejected by the upgrader's origin policy | Configuration error; do not retry |
| 429 | `rate limit exceeded` | Too many upgrade attempts from this source IP | Wait `Retry-After` (seconds), then back off |
| 429 | `connection limit exceeded` | Too many open sockets for this connection key | Close unused sockets; retry after backoff |
| 503 | `service draining` or `manager is not accepting connections` | Node is shutting down | Reconnect after `Retry-After`; a load balancer should route elsewhere |
| 503 | `server at capacity` | Node reached its connection ceiling | Retry after `Retry-After` with jitter |
| 503 | `connection quota reached` | Per-user, per-account or per-tenant limit reached | Close another session of this identity, or retry after backoff |
| 503 | `shard at max capacity` | The user's shard is full | Retry after `Retry-After` with jitter |

The `error` strings in the 503 rows are the current messages; switch on the status and `Retry-After`, not the text. `Retry-After` is in whole seconds and is at least 1. Quota and shard checks run
after authentication but are advisory: two requests racing past them can still
be refused after the upgrade, see close code 1013 below.

The rate limit key is the direct peer IP. `X-Forwarded-For` is ignored, so
clients behind one NAT share a budget (default 100 requests/s, burst 200).

## 2. Close codes the server sends

| Code | Name | Reason text | When | Client action |
|---|---|---|---|---|
| 1001 | Going away | `Server draining`, `Shard stopped` | Node is shutting down or its shard was removed | Reconnect immediately with jitter (0–5 s); the session is lost |
| 1008 | Policy violation | `Too many protocol violations` | `MaxViolations` (default 20) consecutive bad messages | Fix the client. Reconnect only after backoff; a buggy client will be closed again |
| 1008 | Policy violation | `Authentication expired` | Identity `ExpiresAt` passed | Refresh credentials, then reconnect |
| 1008 | Policy violation | caller-supplied (for example `revoked`) | `DisconnectIdentity`, used for revocation or admin kick | Treat as a rejection: re-authenticate; if auth fails, stop |
| 1011 | Internal error | `internal error` | Server could not build the session | Reconnect with backoff |
| 1013 | Try again later | `Outbound queue full` | Client read too slowly and its queue overflowed `SlowConsumerDropThreshold` (default 3) times in a row | Reconnect; if it repeats, the client is too slow for the traffic it subscribes to |
| 1013 | Try again later | `server capacity reached`, `manager stopped or shard capacity reached`, `Shard at max capacity`, `registration rejected`, `Session registration failed` | Admission lost a race after the upgrade, or the registry was unavailable | Reconnect after backoff with jitter |
| 4000 | Session superseded (private use) | `Session superseded` | A newer session with the same session identity replaced this one | **Do not auto-reconnect.** Another tab or device owns the session; ask the user |

Codes the client may also see but the server does not choose: **1000** and
**1001** that the client itself sent are treated as normal and not logged as
errors; **1006** was described above; **1009** (message too big) comes from the
library when a frame exceeds `MaxMessageBytes` (default 1024) and closes the
socket.

The reason text is for logs. It is short and never contains tokens or user data,
but do not parse it: switch on the code, and for 1008/1013 on code plus whether
you can recover.

## 3. The `error` envelope

For a client that sends something wrong the server first warns, and only closes
after the violation count reaches `MaxViolations`. The warning is a text frame:

```json
{"type":"error","data":{"code":"malformed"}}
```

| `code` | Cause |
|---|---|
| `rate_limited` | Messages per second or bytes per second exceeded the connection budget (default 100 msg/s burst 200; 64 KiB/s burst 128 KiB) |
| `malformed` | Frame is not valid UTF-8 JSON, or has no `type` |
| `payload_too_large` | `data` exceeds the registered handler's maximum payload |
| `invalid_payload` | `data` failed the handler's validation |

Rules the client can rely on:

- The envelope carries **only a code**. It does not echo your message or the
  validation detail. Log the offending request on the client side.
- At most **one envelope per second per connection**. A burst of 50 bad
  messages produces one envelope, so the number of envelopes is not the number
  of errors.
- Not every violation is reported. Unknown event types and events the
  authorizer refuses are dropped silently, and an overflowing server queue
  drops the envelope rather than penalising the client.
- Valid events do not produce an envelope. One complete valid event resets the
  consecutive violation counter. Only an unbroken run of `MaxViolations` bad
  messages ends in close 1008.
- `type: "error"` is reserved by the server. Do not register an application
  event with that name.

## 4. Reconnect guidance

1. Use exponential backoff with full jitter: base 1 s, factor 2, cap 30–60 s,
   reset after a connection stays up for a minute. After a node restart every
   client reconnects at once; jitter is what keeps the other node alive.
2. If an HTTP response carries `Retry-After`, wait at least that long before the
   next attempt, then continue with the backoff schedule.
3. Do not auto-reconnect on 4000, on HTTP 426/403, or after a second consecutive
   401. Surface them to the user or operator.
4. After any close, assume messages sent during the gap were **lost**. Fan-out
   through Redis/NATS Core is best-effort; durable events go through EventBus.
   If the application needs gap recovery, resume from your own sequence number.
5. Keepalive: the server pings every `PingPeriod` (default 54 s) and closes the
   socket if no pong arrives within `PongWait` (default 60 s). Browsers and
   standard libraries answer pings automatically; a custom client must too. Set
   proxy and load balancer idle timeouts above 60 s.

## 5. Quick reference for client code

```text
HTTP 429/503 -> wait Retry-After, then backoff
HTTP 401     -> refresh credentials once
HTTP 426/403 -> stop, report

close 1001, 1006, 1011, 1013 -> reconnect with jittered backoff
close 1008 + "Authentication expired" -> refresh credentials, reconnect
close 1008 otherwise -> backoff; if repeated, stop and fix the client
close 4000 -> do not reconnect
```

## 6. Server-side pointers

- Codes are sent by `Connection.requestClose` (while pumps run, via the single
  writer) and `Connection.reject` (before pumps start). `core.CloseSessionSuperseded`
  is the only application code (4000).
- Limits are `ManagerConfig`: `MaxViolations`, `SlowConsumerDropThreshold`,
  `MessagesPerSecond`, `MessageBurst`, `BytesPerSecond`, `ByteBurst`,
  `MaxMessageBytes`, `WriteWait`, `PongWait`, `PingPeriod`.
- Defaults for `MaxViolations` and `SlowConsumerDropThreshold` are reasoned, not
  measured against real clients. Tune them after a soak.
