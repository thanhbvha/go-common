## Highest-priority unfinished fixes

### 1. Make benchmark completion prove durable settlement

Files:

- `examples/eventbus/benchmark/main.go`
- `examples/eventbus/benchmark/main_test.go`
- `eventbus/testdata/benchmark/run-production-scale.ps1`

Current problem:

- The handler increments the completion counter before the engine ACK finishes.
- The runner waits for handler completions and then closes the Bus.
- The final result does not contain final topology statistics.
- The orchestrator does not reject residual pending, delayed, in-flight, lag, or
  DLQ state.

Minimal intended fix:

1. After all expected handler completions, call `DrainTopology` while the
   transport remains open.
2. Read final task topology stats before closing the Bus.
3. Add final `Pending`, `Delayed`, `InFlight`, `DLQ`, `Lag`, and stats-available
   fields to `result.json`.
4. Fail a normal benchmark run unless all final counts are zero.
5. Make the PowerShell orchestrator validate these fields before marking the
   execution completed.
6. Add unit tests for settled and unsettled final-state validation.

Be careful with Kafka's documented stats model: `Pending` may include
fetched-uncommitted obligations while processing, but all obligations must be
zero after `DrainTopology` succeeds.

### 2. Terminate the benchmark child on orchestration failure

File: `eventbus/testdata/benchmark/run-production-scale.ps1`

Current problem:

- Exceptions during broker restart, Docker sampling, parsing, or validation go
  to `finally` and destroy the broker without stopping a still-running benchmark
  process.
- A failed run can therefore leave a long-lived reconnecting process that keeps
  writing artifacts and contaminates later evidence.

Minimal intended fix:

1. In `finally`, if the child exists and has not exited, terminate it before
   Compose teardown.
2. Wait for process termination.
3. Record a `benchmark_process_forced_stop` field in `summary.json`.
4. Add a script-level test using a harmless long-running child or extracted
   cleanup helper.

### 3. Require requested fault actions to occur during active work

Files:

- `eventbus/testdata/benchmark/run-production-scale.ps1`
- `examples/eventbus/benchmark/main.go`
- corresponding tests

Current problem:

- A requested broker restart can be missed if the benchmark exits first, yet
  the run can still be marked completed.
- Kafka `second_worker` currently reports configuration, not proof that the
  second worker started and caused a rebalance during active traffic.
- `SecondWorkerAfter` may be after the sustained production duration as long as
  it is before the overall timeout.

Minimal intended fix:

1. Reject duration-mode fault times greater than or equal to `Duration`.
2. If restart was requested, fail unless `broker_restart_issued` is true.
3. Add an explicit result field proving the second Kafka worker successfully
   started.
4. Record produced/completed/lag values around each fault action so evidence can
   show that work or backlog was active.
5. Do not claim rebalance evidence from the configuration flag alone.

### 4. Fix matrix array invocation

Files:

- `examples/eventbus/benchmark/run-matrix.ps1`
- `eventbus/PRODUCTION_SCALE.md`
- `eventbus/testdata/benchmark/test-scripts.ps1`

Current problem:

- With `powershell.exe -File`, documented values such as
  `-Drivers redis,nats` are received as one string and fail `ValidateSet` rather
  than becoming an array.

Recommended minimal fix:

- Accept comma-delimited strings for Drivers, Workloads, PayloadKB,
  Concurrency, and Messages, split them inside the script, and validate every
  resulting value.
- Add a `-ValidateOnly` mode to the matrix script so the exact documented CLI
  can be tested without Docker or workloads.
- In duration mode, reject multiple `Messages` values or avoid iterating over a
  dimension that does not control production.

### 5. Make Bus contract cleanup failure-safe

File: `eventbus/contracttest/suite.go`

Current problem:

- A Bus is drained only at the successful end of each subtest.
- If an assertion calls `t.Fatal` after `Start`, workers can remain active while
  transport cleanup runs.

Minimal intended fix:

- Register a `t.Cleanup` immediately after opening each Bus. Use a bounded
  `Close` context and ignore `ErrBusClosed`/already-completed shutdown behavior.
- Keep explicit `Drain` calls for behavioral assertions; cleanup is only the
  failure safety net.
- Ensure blocking handler channels are also released or canceled by cleanup.

  and Kafka. Production-scale scheduler ownership changes remain part of the
  fault/soak evidence matrix.

  FIFO within one physical topic-partition; transitions among main, delay, and
  subscriber-private topics are independent logs. Memory, Redis, and NATS do
  not advertise ordering.

  and Kafka. The scenario preserves each driver's exposed logical message
  identity, ACKs the redelivery, and requires final stats to return to zero.
  Kafka may retain envelope attempt `1` when replaying an uncommitted offset;
  handlers still require idempotency under the at-least-once contract.
